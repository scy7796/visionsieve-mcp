# 宣傳文字與技術指標核對

本文件列出發布時的核心技術特點、驗證狀態，以及各項證據可支持的宣傳文字。

## 核心定位

本專案讓以文字為主的 Agent（如 DeepSeek 或 OpenCode）維持主控，僅在答案需要像素證據時，透過唯讀的 MCP 工具呼叫 Luna，取得結構化的關鍵證據。回傳內容以簡短結論為主，避免完整圖檔、原始 OCR 文字或冗長推理持續占用主要對話的上下文。

## A 級：適合放在首頁的重點

| 特點 | 建議表述 | 依據 | 驗證狀態 |
|---|---|---|---|
| 保留主代理 | 讓 DeepSeek/OpenCode 維持主控，只在需要像素證據時呼叫 Luna | MCP 分開處理視覺辨識與規劃、程式開發 | 本機程式碼與契約已驗證 |
| 受控視覺證據流程 | 一個唯讀工具統一完成路徑授權、圖片處理、結構化證據及最終驗證 | 處理流程包含圖片轉送以外的授權與驗證 | 本機程式碼、測試及審查已驗證 |
| 最小上下文 | 預設只回傳答案、可定位的證據、相關文字及不確定性 | reducer、嚴格 Schema 及輸出預算共同限制內容 | 本機測試已驗證 |
| 不擅自切換計費路徑 | 預設要求透過 ChatGPT 登入，移除 API 計費變數；Luna 無法使用時回報失敗 | 避免設定為訂閱模式，實際卻走 API 計費 | 命令建構與迴歸測試已驗證；帳號仍須透過實際探針確認 |
| 實機像素驗收 | 一鍵流程要求通過登入驗證、網路連線與隨機像素探針，確認實際具備圖片辨識能力 | 避免安裝成功卻無法呼叫的情況 | 安裝腳本已驗證 |
| 失敗時拒絕回傳（fail-closed） | 模型身分、Schema、語意完整性或提示注入最終檢查失敗時，不回傳不實證據 | 明確回報失敗，不在未告知的情況下由未知模型替代 | 本機測試已驗證 |

## B 級：適合技術頁或發布說明

| 特點 | 準確表述 | 注意事項 |
|---|---|---|
| 自適應影像處理 | 內建穩定讀取、受控暫存、裁切、長圖分塊及失敗重試 | 可以說明具備這些機制；沒有消融實驗時，不能宣稱「成功率提升 X%」 |
| 圖片提示注入防護 | 將圖片文字視為不可信內容；Codex 子行程停用 shell、子代理、hooks、遠端外掛及網頁搜尋，結果另須通過提示注入最終檢查 | 不應宣稱「絕對防注入」或「完全沙箱」 |
| 檔案安全 | 授權根目錄、symlink/junction/reparse、TOCTOU、像素炸彈及異常檔案防護 | 適合放在安全模型章節，不必占用首頁篇幅 |
| 隱私預設值 | 預設不儲存原始服務提供者回應、完整 OCR，也不向主程式回傳絕對快取路徑 | 仍須說明圖片會傳送至設定的遠端視覺後端 |
| 簽章快取 | 快取綁定實際傳送的位元組及影響結果的設定，命中時後端呼叫次數為 0 | 不宣稱「本機快很多」；主要價值是避免重複呼叫遠端後端 |
| 單一工具介面 | 僅向主程式提供 `vision.inspect`，減少工具選擇及權限範圍 | 簡單是優點，但不代表視覺品質已獲驗證 |
| 快速本機回應 | 參考建置電腦的本機協調耗時低於 100 ms，完整迴歸測試約需數秒 | 必須附上環境與量測範圍，不能將數字當成實際 Luna 延遲 |

## C 級：實機驗收通過後，才能加入發布頁

- 目前帳號可透過 ChatGPT/Codex 訂閱，實際呼叫 `gpt-5.6-luna`；
- 實際端到端延遲的 median、p95、min、max；
- Windows、macOS、Linux 一鍵安裝結果；
- Codex、OpenCode/DeepSeek 等主程式都能實際找到並呼叫工具；
- 重複呼叫同一張圖片時確實不再請求 Luna，並量化節省的時間；
- 長圖及小字樣本啟用裁切、分塊後，相較於停用重試的成功率提升；
- 在同一帳號、同一圖片及同一 Luna 設定下，與 Codex 原生附圖比較正確率、延遲及輸出長度；
- 主代理上下文或 token 的實際節省量；
- 提示注入測試集上的攔截率及誤拒率。

## 目前不得使用的宣傳主張

- 「視覺準確率全面超過 OpenAI 官方原生方案」；
- 「比所有視覺 MCP 更快、更準」；
- 「Luna 視覺能力必然強於任何旗艦模型」；
- 「絕不會產生 API 費用」或「伺服器一定按訂閱結算」；
- 「完全沙箱化」、「絕對安全」或「100% 防提示注入」；
- 「所有 ChatGPT 帳號都能使用 Luna」；
- 「快取零延遲」或「快取讓本機處理快 X 倍」；
- 未完成同機對照，就宣稱「比官方節省 X% token 或時間」。

## 與官方原生方案比較

當使用者臨時需要看一張圖片，且 Codex 本身就是主代理時，原生附圖通常更直接。

Visual Evidence Gateway 的優勢適用於以下系統需求：

1. 主代理是 DeepSeek/OpenCode，不希望為了少數圖片步驟轉移整個任務；
2. 需要路徑授權、唯讀邊界及最小上下文回傳；
3. 需要結構化證據、圖片索引、不確定性及模型身分驗證；
4. 需要長圖、小圖的裁切分塊重試、簽章快取，以及失敗時拒絕回傳的機制；
5. 需要將「是否確實能透過訂閱讀取像素」列為安裝必要檢核。

因此，首頁應寫「更適合跨主代理的受控視覺委派」，不要寫「原生視覺的全面替代品」。

## 建議首頁文案

英文：

> **Keep your main agent. Add a controlled Luna vision evidence path.**
>
> Visual Evidence Gateway gives DeepSeek, OpenCode, and other text-first agents one read-only tool for pixel-dependent work— with path authorization, adaptive image retries, strict evidence schemas, prompt-injection containment, minimal-context returns, and no silent API-key fallback.

中文：

> **保留你的主代理，加入受控的 Luna 視覺證據流程。**
>
> Visual Evidence Gateway 讓 DeepSeek、OpenCode 等以文字為主的代理，僅在答案需要像素證據時呼叫 Luna。單一唯讀 MCP 工具統一處理路徑授權、自適應裁切與分塊、嚴格證據 Schema、圖片提示注入防護及最小上下文回傳，並禁止在未告知的情況下切換至 API 計費。

## 發布後優先改善的五個項目

1. 建立 100–300 張真實開發截圖的基準測試，依 OCR、UI、圖表、錯誤訊息、長圖及多圖比較分類；
2. 在同一部電腦上比較 `Visual Evidence Gateway`、原生附圖、OCR 與輕量 MCP，不跨帳號比較；
3. 分別對裁切與分塊、快取及提示注入最終檢查進行消融實驗，量化各機制的實際貢獻；
4. 在 Windows/macOS/Linux 及 Codex/OpenCode 兩類主程式中執行測試矩陣；
5. 自動將實測結果產生為機器可讀的 JSON，並僅由驗證腳本更新 README 的「實測結果」區，避免手動誇大或數據偏移。
